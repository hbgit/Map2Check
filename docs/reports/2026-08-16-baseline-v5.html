What the failures actually are

Every false positive was traced to its raw output and its source. Three distinct causes, and only one of them is a defect in Map2Check.

33 of 36 false positives answer the wrong question

Benchmark mapping

Every one of them returns FALSE-MEMTRACK — a memory-leak verdict — on a program labelled safe. They are not wrong. Juliet's CWE-416 "good" variants leak by construction, and say so in their own comments: 

static void goodG2B() {
    data = (int *)malloc(100*sizeof(int));
    ...
    printIntLine(data[0]);
    /* POTENTIAL INCIDENTAL - Possible memory leak here if data was not freed */
}

good() calls goodG2B() and then goodB2G(), so every CWE-416 good program leaks 400 bytes. The runner maps CWE-416 to --memtrack, which checks for leaks as well as use-after-free — so Map2Check is asked the leak question and answers it correctly. That is why CWE-416 shows TN = 0: no safe program can pass a leak check it was built to fail. The same mechanism produces the 9 FPs in CWE-122 and the 3 in CWE-476.

Excluding these 33, Juliet precision is 99.2%.

3 genuine false positives, all in the i64 path

Tool defect

The only real false alarms in 2,525 cases are the int64_t_rand_square good variants. Their guard is: 

if (imaxabs((intmax_t)data) <= sqrtl(LLONG_MAX)) {
    int64_t result = data * data;
}

With data now symbolic, KLEE cannot reason about the floating-point comparison and drops it: 

KLEE: WARNING ONCE: silently concretizing (reason: floating point) expression (Xor w64 ...)
KLEE: WARNING ONCE: calling external: sqrtl(303375153036227285876734)

Note the argument — 3.03e23, not LLONG_MAX's 9.22e18. The guard's constraint is lost, the branch is taken with data unconstrained, and data * data overflows. The overflow checker is right; the path leading to it is not real.

Cost of the rand() fix, stated plainly

Making rand() nondeterministic converted 6 known false negatives into true positives — and introduced these 3 false positives. Symbolic input is what exposed that floating-point guards are not modelled. Net positive, but it is a trade, not a pure win.

Those four sources sitting on exactly 50.0% is the signature of a systematic failure, not noise: the safe variant is proven safe and the vulnerable variant is missed, every time. When input arrives through an unmodelled I/O call, Map2Check explores the trivial path and reports TRUE.

This is the single highest-leverage finding in the baseline. It is the same root cause as the rand() false negatives and the sqrtl false positive: unresolved external functions. Fixing it at the tool level — modelling an unmodelled external as nondeterministic input rather than letting KLEE call it concretely — would move ~340 timeouts and a large share of the 404 false negatives at once, and would generalise to every benchmark rather than to Juliet alone.

Where the tool stands

Map2Check is precise. Corrected for benchmark-mapping artifacts, it is at 100% precision on CASTLE and 99.2% on Juliet — a reported bug is a real bug. Memory safety is its strongest ground: double free, null deref and leak detection are at or near perfect recall on both suites.

What limits it is reach, and reach is limited by one thing far more than any other. The overflow work validated in this run — the width-aware i64 ABI — is functioning: 60 TP on CWE-190 and 48 on CWE-191, with the int64_t families exercised for the first time. Its recall reads low only because 268 of those cases never got a decidable input.

The properties that genuinely need new capability are the reachability family: type confusion, wrong-argument calls, unbounded allocation and infinite loops, all currently approximated rather than checked.

Next

  1. Model unresolved externals as nondeterministic input One change, three symptom classes: ~340 timeouts, a large share of 404 FNs, and the concretization FP. Generalises beyond Juliet, unlike the per-benchmark rand() stub.
  2. Separate the use-after-free property from the leak property CWE-416 is scored against --memtrack, which conflates the two and makes TN unreachable. Count only FALSE-FREE / FALSE-DEREF as detection there.
  3. Fix witness line attribution CASTLE-822-3 finds the bug and points at the wrong line. Cheap to fix, and it is the difference between 98.2% and 100% reported precision.
  4. Exclude the decodeHexChars variants from scope The stub returns 0, turning real bugs into trivially safe programs that inflate TN. Excluding is honest; stubbing is not.
  5. Raise PER_FAMILY once externals are modelled Family coverage is complete; variant coverage is 3 of ~26. Worth deepening only after the input-modelling fix, since today it would mostly re-measure timeouts.
